# YearWeGo backup archive format, version 1

This document describes the file that YearWeGo writes when someone makes a backup (Settings → Backup), so that anyone can open it without the app. It is the source of truth for the published reader (`yearwego-reader`). Any change to a layer described here bumps a version and updates this file and `vectors.json` in the same pull request.

- **Status:** describes the app as of 2026-10-29 (`backupFormatVersion` 1).
- **Known-answer vectors:** `docs/archive-format/vectors.json`, produced and checked by `lib/crypto/encryption/archive-format.vectors.test.ts`.
- **Sources:** every rule below names the app file and line it comes from. Paths are relative to the app repository root.

## 1. Overview

A backup is one zip file. Inside it, one plaintext header and one encrypted blob. Inside the blob, a second zip holding a manifest, a plaintext SQLite database, and the encrypted audio files. Inside the database, the person’s words are encrypted row by row.

```
<ts>.yearwego.backup.zip                      outer zip, not encrypted
├── <ts>.yearwego.header.json                 plaintext: KDF salt and parameters
└── <ts>.yearwego.data.encrypted              "YWG1" blob = XChaCha20-Poly1305(inner zip)
    └── (inner zip)
        ├── manifest.json                     entry list, sizes, checksums, manifest hash
        ├── <ts>.yearwego.backup.db           plaintext SQLite 3 database
        └── recordings/<stamp>.aac.encrypted  "YWGA" chunked, encrypted audio, one per take
```

Keys, from the passphrase down:

```
passphrase ──Argon2id(header salt)──────────────▶ archive key ──▶ opens the inner zip
passphrase ──Argon2id(crypto_key_backups.kdf_salt)▶ backup key ──▶ root key (crypto_key_backups row)
root key ──▶ data encryption key (DEK), one per recording (crypto_keys rows)
DEK ──▶ that recording’s transcript text and its audio file
```

The passphrase is stretched twice, with two different salts: once for the archive and once for the key row inside the database. Both runs use the same parameters. A reader needs about 256 MiB of memory for each run, on top of the archive held in memory.

`<ts>` is the local time the backup began, formatted `yyyy-MM-dd_HH-mm-ss` (`features/backup/consts/backups.ts:5-9`). The outer file is named `<ts>.yearwego.backup.zip` (`features/backup/lib/backup.service.ts:43-45`).

## 2. Primitives

All from libsodium. A browser needs libsodium.js **sumo** (the standard build lacks `crypto_pwhash`).

| Use                   | Primitive                                      | Parameters                                                                 |
| --------------------- | ---------------------------------------------- | -------------------------------------------------------------------------- |
| Passphrase stretching | `crypto_pwhash`, Argon2id v1.3 (`algorithm` 2) | 32-byte output, `opsLimit` 3, `memLimit` 268435456 (256 MiB), 16-byte salt |
| Encryption            | `crypto_aead_xchacha20poly1305_ietf`           | 32-byte key, 24-byte nonce, 16-byte tag appended to the ciphertext         |
| Checksums             | `crypto_generichash` (BLAKE2b, unkeyed)        | 8-byte output for entries and keys, 32-byte for the manifest hash          |

Sources: KDF call `lib/crypto/encryption/keys/backup-key.ts:48-60`; parameter values `lib/crypto/encryption/constants.ts:51-55` and `:81-90` (MODERATE limits; `crypto_pwhash_ALG_DEFAULT` is 2, Argon2id13); AEAD `lib/crypto/encryption/algorithms/xchacha20.ts:14-116`; checksum `lib/crypto/encryption/utils/integrity.ts:3-21`; manifest hash `features/backup/lib/backup.service.ts:41,551-555`.

There is no `crypto_secretstream` anywhere in the format (`lib/crypto/encryption/streaming/chunked-recording.ts:17-21`).

## 3. Associated data (AAD)

Every ciphertext is bound to where it lives by an associated-data string. The string is UTF-8 (in practice ASCII), built as fields joined by `|`, always starting with the version field `v1` (`lib/crypto/encryption/authenticated-context.ts:17-19,168-178`). Identifiers are UUID strings exactly as stored in the database; no field may contain `|`.

| What                                                       | AAD                                                                                                                                                                    | Source                                                                                       |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Inner zip                                                  | `v1\|backup.archive\|<backupFormatVersion>\|<header salt, as written in the header>`                                                                                   | `authenticated-context.ts:241-242`; `backup.service.ts:320-330`                              |
| Root key in `crypto_key_backups`                           | `v1\|crypto_key_backup\|<crypto_key_backups.crypto_key_id>`                                                                                                            | `authenticated-context.ts:186-187`; `features/backup/lib/key-backup.service.ts:230-237`      |
| DEK in `crypto_keys`                                       | `v1\|crypto_key.data_encryption_key\|<crypto_keys.id>`                                                                                                                 | `authenticated-context.ts:184-185`; `lib/services/crypto_keys.ts:138-147`                    |
| Transcript text                                            | `v1\|transcript.text\|<transcripts.id>`                                                                                                                                | `authenticated-context.ts:205-206`; `features/transcription/services/transcripts.ts:296-309` |
| One audio chunk                                            | `v1\|recording.audio.chunk\|<recordings.id>\|<recordings.crypto_key_id>\|<file nonce, 32 lowercase hex>\|<sample rate>\|<channels>\|<chunk index>\|final` or `…\|more` | `authenticated-context.ts:190-200`; `chunked-recording.ts:172-191`                           |
| Legacy whole-file audio (not written by any shipped build) | `v1\|recording.audio\|<recordings.id>\|<recordings.crypto_key_id>`                                                                                                     | `authenticated-context.ts:188-189`                                                           |

Numbers are written in decimal with no padding (`String(n)`). For the archive, the salt is the header’s `salt` string itself, byte for byte (base64 URL-safe without padding), and the version is `1`, so a real AAD looks like `v1|backup.archive|1|qE5NlRoS8hXMMXw0UXGEAQ`.

## 4. The passphrase

- The app generates eight words from the EFF large wordlist (7,776 words), lowercase, joined by `-` (`lib/crypto/encryption/passphrases/generatePassphrase.ts:6-7,19-40`). Example shape: `acorn-anthem-bronze-canopy-harbor-lantern-quilt-velvet`.
- It is used **byte for byte**, as UTF-8, with no trimming or case folding (the restore screen passes the field’s text straight through: `features/restore/components/restore/steps/enter-passphrase-step.tsx:77-84`; `backup-key.ts:51-58`).
- Development builds can use the fixed passphrase `TEST` (`generatePassphrase.ts:10-12,25-28`).
- A reader may, after the exact text fails, retry once with surrounding spaces removed and letters lowercased. That retry costs one more Argon2id run.

## 5. Outer zip

A standard zip with two entries at its root (`backup.service.ts:232-262,345-356`):

1. `<ts>.yearwego.header.json`
2. `<ts>.yearwego.data.encrypted`

The iOS app writes it with `react-native-zip-archive` (SSZipArchive), which stores names relative to the zipped folder and deflates. Readers should accept stored or deflated entries, ignore directory entries, and find the two files by their suffixes, as the app’s own restore does (`features/restore/lib/restore.service.ts:180-190,218-225`). Some systems unzip a downloaded zip on their own; a reader can accept the two loose files instead.

### 5.1 Header (`*.yearwego.header.json`)

Plaintext JSON, written with `JSON.stringify(value, null, 2)` (`backup.service.ts:246-260`):

```json
{
  "salt": "qE5NlRoS8hXMMXw0UXGEAQ",
  "backupFormatVersion": 1,
  "kdfParams": {
    "keyLength": 32,
    "opsLimit": 3,
    "memLimit": 268435456,
    "algorithm": 2
  }
}
```

- `salt`: the 16-byte Argon2id salt, base64 **URL-safe without padding** (libsodium’s default variant, `node_modules/react-native-libsodium/src/lib.native.ts:240-247`). 22 characters.
- `backupFormatVersion`: `1`. A header without it is treated as version 0 and refused (`restore.service.ts:489-498`). Check the version **before** decrypting: it is part of the AAD, so a mismatch would otherwise look like a wrong passphrase (`restore.service.ts:273-278`).
- `kdfParams`: the Argon2id inputs. Version 1 always writes the values above. A reader should refuse values it does not expect rather than spend unbounded memory.

### 5.2 Sealed inner zip (`*.yearwego.data.encrypted`)

One XChaCha20-Poly1305 operation over the entire inner zip, packed as a `YWG1` blob (`backup.service.ts:295-330`; `lib/crypto/encryption/utils/pack.ts:13-44`):

| Offset | Length | Value                             |
| ------ | ------ | --------------------------------- |
| 0      | 4      | `59 57 47 31` (ASCII `YWG1`)      |
| 4      | 1      | `01` (blob format version)        |
| 5      | 24     | nonce, random                     |
| 29     | rest   | ciphertext ‖ 16-byte Poly1305 tag |

- Key: `crypto_pwhash(32, passphrase, base64urlDecode(header.salt), 3, 268435456, 2)`.
- AAD: `v1|backup.archive|1|<header.salt>`.
- Authentication failure means the passphrase is wrong **or** the file is damaged; the two cannot be told apart (`restore.service.ts:293-305`).

The `YWG1` packing is used only for the archive. Database columns store their nonce and ciphertext in separate columns with no header (sections 7–8).

## 6. Inner zip

Made by zipping the folder `backups/<ts>/data/` (`backup.service.ts:122-170`). Entries, relative to that folder:

- `manifest.json`
- `<ts>.yearwego.backup.db`
- `recordings/<stamp>.aac.encrypted`, every file in the app’s recordings folder (`features/backup/lib/actions/handleExportEncryptedAudio.ts:5-33`). A backup from someone who has only typed has no `recordings/` folder at all.

### 6.1 Manifest (`manifest.json`)

Written with `JSON.stringify(manifest, null, 2)` (`backup.service.ts:386-463`; type `features/backup/lib/backup.types.ts:6-48`). Keys, in this order:

```json
{
  "backup_id": "uuid",
  "created_at": "2026-10-29T12:31:26.000-04:00",
  "updated_at": "…same…",
  "app": { "app_id": "yearwego", "bundle_id": "…", "build_number": "…", "version": "1.0.0" },
  "database": { "filename": "<ts>.yearwego.backup.db" },
  "backup_format_version": 1,
  "created_with_versions": { "app_version": "…", "build_number": "…", "os_version": "…" },
  "entries": [
    { "path": "<ts>.yearwego.backup.db", "type": "…", "size": 123, "checksum": "16 hex chars" },
    {
      "path": "recordings/2026-10-26T11-10-00-000Z.aac.encrypted",
      "type": "…",
      "size": 456,
      "checksum": "…"
    }
  ],
  "encryption": { "table": "crypto_key_backups", "crypto_key_backup_id": "uuid or null" },
  "device": { "platform": "ios", "model": "…", "os_version": "…" },
  "metadata": { "schema_tag": "20261029134647_milestones", "entry_count": 2, "total_bytes": 579 },
  "manifest_hash": "64 hex chars"
}
```

- `entries[].checksum`: BLAKE2b, 8-byte output, lowercase hex, over the entry’s bytes (`backup.service.ts:507-542`). The manifest itself is not listed.
- `entries[].type`: whatever the platform’s file API reports. Informational only.
- `manifest_hash`: BLAKE2b, 32-byte output, lowercase hex, over the UTF-8 of `JSON.stringify` (compact, no spaces) of the manifest **without** the `manifest_hash` key, keys in the order they appear in the file (`backup.service.ts:450-455,551-555`). To check it: parse the file, delete `manifest_hash`, stringify compactly, hash (`restore.service.ts:110-163`).
- The app’s restore also checks `entry_count`, `total_bytes`, unique and safe paths (no leading `/`, no `..`), and that exactly one entry is the database (`restore.service.ts:110-169`).
- `encryption.crypto_key_backup_id` names the `crypto_key_backups` row that matches this archive’s passphrase. Archives made before 2026-10-02 carry `null` here (`.postmortems/2026-10-02-lost-passphrase-backup-carried-old-key-row.md`).

The manifest is not signed; it sits inside the authenticated blob, so its integrity comes from the archive’s AEAD tag. The checksums catch damage introduced between building the inner zip and sealing it.

### 6.2 Database (`<ts>.yearwego.backup.db`)

A **plaintext** SQLite 3 file, not SQLCipher: the live database is SQLCipher, and the backup exports it with `sqlcipher_export` into an attachment keyed with the empty key, or with `VACUUM INTO` on a plaintext build (`features/backup/lib/db-backup/backup.ts:9-56`). Any SQLite build opens it. The person’s words inside it are still encrypted, column by column.

Timestamps are integers, milliseconds since the Unix epoch, UTC (drizzle `timestamp_ms`). Booleans are integers `0`/`1`. Identifiers are UUID strings (UUIDv7 for rows made since the August 2026 migration). Blobs are raw bytes.

## 7. Keys

### 7.1 Root key from `crypto_key_backups`

Schema `lib/db/schema/crypto_key_backups.ts:6-29`:

| Column            | Meaning                                                                    |
| ----------------- | -------------------------------------------------------------------------- |
| `id`              | row id; the manifest’s `encryption.crypto_key_backup_id`                   |
| `crypto_key_id`   | the `crypto_keys` row of the root key it wraps (type `key_encryption_key`) |
| `encrypted_key`   | ciphertext ‖ tag (48 bytes)                                                |
| `nonce`           | 24 bytes                                                                   |
| `kdf_salt`        | 16 raw bytes (not base64)                                                  |
| `kdf_params_json` | e.g. `{"keyLength":32,"opsLimit":3,"memLimit":268435456,"algorithm":2}`    |
| `hint`            | unused; null                                                               |

Steps (`features/backup/lib/key-backup.service.ts:99-142` reads it; `:201-264` writes it):

1. Pick the row: the one whose `id` is the manifest’s `crypto_key_backup_id`; otherwise the one whose `crypto_key_id` is the active root key (the `crypto_keys` row of type `key_encryption_key` with the highest `version`, then newest `created_at`: `lib/services/crypto_keys.ts:259-275`; `features/backup/services/crypto_key_backups.ts:73-98`). A reader may try every row.
2. Backup key = `crypto_pwhash(32, passphrase, kdf_salt, opsLimit, memLimit, algorithm)` from that row’s own `kdf_params_json`. This is the **second** Argon2id run; its salt differs from the header’s.
3. Root key = `XChaCha20-Poly1305-decrypt(encrypted_key, nonce, AAD "v1|crypto_key_backup|<crypto_key_id>", backup key)`, 32 bytes.
4. Optionally confirm it: BLAKE2b-8 of the root key equals the `checksum` of the `crypto_keys` row named by `crypto_key_id`.

**Older archives may need a second passphrase.** Before 2026-10-02, a backup made right after “I’ve lost my passphrase” sealed the archive under the new passphrase but carried the key row from the old one, and a first backup by someone who had skipped the onboarding passphrase carried no row at all (`.postmortems/2026-10-02-lost-passphrase-backup-carried-old-key-row.md`; fix at `features/backup/lib/backup.service.ts:63-67`). A reader should ask for an earlier passphrase when the archive opens but step 3 fails. With no row at all, the words and audio cannot be recovered from the archive alone.

### 7.2 Data encryption keys (`crypto_keys`)

Schema `lib/db/schema/crypto_keys.ts:5-30`: `id`, `encrypted_key` (48 bytes), `nonce` (24), `checksum` (8), `type` (`key_encryption_key` or `data_encryption_key`), `version`.

For each row of type `data_encryption_key` (`lib/services/crypto_keys.ts:129-214`):

- DEK = `decrypt(encrypted_key, nonce, AAD "v1|crypto_key.data_encryption_key|<id>", root key)`, 32 bytes.
- Check: BLAKE2b-8(DEK) equals `checksum`.

The `key_encryption_key` row’s own `encrypted_key` is the root key wrapped by the phone’s device key (AAD `v1|root_key.securestore|root_encryption_key_v1`), which never leaves the phone. A reader cannot and need not open it.

Each recording has its own DEK, named by `recordings.crypto_key_id`.

## 8. Words: `transcripts`

Schema `lib/db/schema/transcripts.ts:21-159`. One row per recording at most (`recording_id`, unique).

- `encrypted_text`: ciphertext ‖ tag; `text_nonce`: 24 bytes. Both null until transcription finishes.
- Text = UTF-8 of `decrypt(encrypted_text, text_nonce, AAD "v1|transcript.text|<transcripts.id>", DEK of the recording)` (`features/transcription/services/transcripts.ts:218-255,296-309`).
- `model_id` is `text-entry` for something the person typed (`transcripts.ts:257-292`).
- `transcript_quality` is `empty` or `insufficient` when the words could not be made out; null otherwise.

A **typed entry** is a `recordings` row with `src` null and a transcript; a **spoken entry** has `src` set and, once transcribed, a transcript (`features/recording/services/logbook.ts:133-134`).

## 9. Audio: `YWGA` chunked recordings

Each spoken take is one file, `recordings/<src>` in the inner zip, where `<src>` is `recordings.src`: a bare file name such as `2026-10-26T11-10-00-000Z.aac.encrypted` (`lib/db/schema/recordings.ts:24`). Rows from older builds may store a full `file://…/recordings/<name>` URI; use the last path segment, percent-decoded (`consts/recordings.ts:20-31`).

Source: `lib/crypto/encryption/streaming/chunked-recording.ts` (writer `features/recording/lib/streaming/encrypted-recording-writer.ts:85-200`).

### 9.1 File header, 27 bytes (`chunked-recording.ts:42-56,109-155`)

| Offset | Length | Value                                                                                                                                        |
| ------ | ------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 0      | 4      | `59 57 47 41` (ASCII `YWGA`)                                                                                                                 |
| 4      | 1      | `01` (format version)                                                                                                                        |
| 5      | 16     | file nonce, random per file                                                                                                                  |
| 21     | 4      | sample rate, unsigned 32-bit little-endian (the app records at 48000: `features/recording/hooks/useRecord.ts:50`; the dev seed writes 44100) |
| 25     | 1      | channels (`1`)                                                                                                                               |
| 26     | 1      | codec: `01` = AAC-LC in ADTS frames, the only value                                                                                          |

### 9.2 Chunks (`chunked-recording.ts:193-239`)

Immediately after the header, repeated to the end of the file:

| Length | Value                                                              |
| ------ | ------------------------------------------------------------------ |
| 4      | ciphertext length _n_, unsigned 32-bit little-endian (at least 16) |
| 1      | flags; bit 0 = FINAL                                               |
| _n_    | ciphertext ‖ tag                                                   |

For the chunk at position _i_ (0, 1, 2, … in file order):

- Nonce (24 bytes) = file nonce (16) ‖ _i_ as unsigned 64-bit little-endian (`chunked-recording.ts:157-164`). Nonces are never stored.
- AAD = `v1|recording.audio.chunk|<recordings.id>|<recordings.crypto_key_id>|<file nonce hex>|<sample rate>|<channels>|<i>|final` if the FINAL flag is set, else `…|more`.
- Key = the recording’s DEK.
- Plaintext = `[levelCount: 1 byte][levels: levelCount bytes][ADTS frames]`. Levels are loudness samples (0–255) for the waveform. Frames are whole ADTS AAC frames, never split across chunks; each chunk holds about 200 ms.

The last chunk is a FINAL marker: flag bit 0 set, plaintext exactly one byte `00` (no levels, no audio), so its ciphertext is 17 bytes (`chunked-recording.ts:197-218,345-351`). Nothing may follow it.

### 9.3 Getting playable audio

Concatenate every non-FINAL chunk’s frames in order. The result is a raw ADTS AAC stream, playable as a `.aac` file (`audio/aac`) in current Safari, Chrome, and Firefox (`chunked-recording.ts:253-274`). The app repackages it into `.m4a` for playback (`features/recording/lib/actions/handleDecryptRecording.ts:86-104`); that step is optional.

Tolerance (`chunked-recording.ts:241-252,304-368`):

- A missing FINAL marker or a partial last chunk means the take was cut short (a crash, a dead battery). Everything before it is still valid audio; keep it.
- A complete chunk that fails authentication is damage or tampering, not truncation. Stop there.
- Duration = number of ADTS frames × 1024 ÷ sample rate.

## 10. Rebuilding the Logbook

The app’s Logbook reads the database in `listLogbookSessions` (`features/recording/services/logbook.ts:68-151`) and the aims in `listAims` (`features/loops/services/aim.ts:24-45`). The tables are in `lib/db/schema/`.

### 10.1 Tables

- `sessions` (`lib/db/schema/sessions.ts:7-86`): `id`, `created_at`, `check_at` (when the check-in was due), `done_at`, `confirmed_at`, `did_goal` (`1` did it, `0` didn’t, null not answered), `flow`, `status_id`.
- `recordings` (`lib/db/schema/recordings.ts:9-69`): `id`, `session_id`, `created_at`, `src`, `duration_ms`, `status_id`, `recording_type_id`, `prompt_key`, `crypto_key_id`, `waveform_peaks` (JSON array of 0–255), `source` (`phone` or `watch`).
- `transcripts` (section 8).
- `milestones` (`lib/db/schema/milestones.ts:9-31`, added 2026-10-29 by `lib/db/migrations/20261029134647_milestones.sql`): `id`, `created_at`, `recording_id`, `reached_at`, `closed_at`.

Values (`features/loops/lib/flow/flow.ts:1-8`; `lib/validation/statuses.z.ts:3-9`; `lib/validation/recording-types.z.ts:3-18`):

- `flow`: `core` (a day), `aim` (where you’re headed), and in older archives `compass` (about 30 days) and `horizon` (a year).
- `status_id`: `pending`, `active`, `done`, `failed`, `unknown`.
- `recording_type_id`: `goal`, `celebration`, `fail_reason`, `reflection`, `roadblock_intent`, `other`.

### 10.2 A day

For each `sessions` row with `flow = 'core'` and `status_id != 'pending'`, newest `created_at` first (`logbook.ts:94-111`):

- Take its `recordings` with `status_id = 'done'` and `recording_type_id` in (`goal`, `celebration`, `fail_reason`). When there are several of one type, the newest `created_at` is the current take (`logbook.ts:143-148`).
- Skip a session with none.
- **Intention:** the `goal` recording. Its words are its transcript; its question is “Today, I’ll…” (or “My smallest step today is…” when `prompt_key` is `core.setGoal.smallestStep`).
- **Did you do it?** from `did_goal`: `1` = did it; `0` = didn’t; null with `status_id = 'active'` = still waiting for its check-in; null otherwise = closed without an answer (`logbook.ts:59-64`).
- **The answer:** the `celebration` recording answers “What are you proud of?”; the `fail_reason` recording answers “What got in the way?”.
- The day’s date is the session’s `created_at` in the reader’s local time.

### 10.3 Where you’re headed

- **With a `milestones` table** shaped as above (it has `closed_at` and no `session_id`): every row, newest `created_at` first, joined to its `recording_id`. The open one (`closed_at` null) is the current heading; `reached_at` is when the person said they got there (`aim.ts:24-45,72-109`). Its words are that recording’s transcript; its question is “I want…”.
- **Without one:** use `sessions` with `flow = 'aim'` and `status_id = 'done'`, and the newest `done` `goal` recording of each. It was reached when the session has `did_goal = 1`, at `confirmed_at`; it closed when the next aim was recorded. This is exactly the backfill the 2026-10-29 migration ran (`lib/db/migrations/20261029134647_milestones.sql:23-53`).
- Archives made before 2026-10-29 can hold an **unrelated** older `milestones` table (it has `session_id`, `journey_id`, and `encrypted_title`; created in `lib/db/migrations/20260828132118_baseline.sql:333-361`, dropped in `20261029040745_core_loop_drop_cut_tables.sql`). Ignore that table and use the `aim` sessions, if any.

### 10.4 Questions

`recordings.prompt_key` names the question each take answered; when it is null, derive it from the session’s flow and the recording type (`features/loops/content/prompts.ts:97-190`).

| `prompt_key`                | Question                                            |
| --------------------------- | --------------------------------------------------- |
| `aim.want`                  | I want…                                             |
| `core.setGoal`              | Today, I’ll…                                        |
| `core.setGoal.smallestStep` | My smallest step today is…                          |
| `core.checkIn.celebrate`    | What are you proud of?                              |
| `core.checkIn.learn`        | What got in the way?                                |
| `compass.setGoal`           | What matters to you in the next 30 days?            |
| `compass.refine`            | What matters most for the next 30 days?             |
| `compass.checkIn.celebrate` | What moved you closer? Call out your wins.          |
| `compass.checkIn.learn`     | What got in the way, and what will you change?      |
| `horizon.setGoal`           | What matters to you in the year ahead?              |
| `horizon.reInvite`          | A new year. What matters to you now?                |
| `horizon.reflect`           | What still matters to you, what fell away, and why? |

Fallback when `prompt_key` is null (`prompts.ts:148-167`): `aim`+`goal` → `aim.want`; `core`+`goal`/`celebration`/`fail_reason` → `core.setGoal`/`core.checkIn.celebrate`/`core.checkIn.learn`; `compass` likewise with `compass.*`; `horizon`+`goal` → `horizon.setGoal`, `horizon`+`reflection` → `horizon.reflect`.

### 10.5 Older archives

Tolerate all of these:

- **Compass and horizon sessions** (archives before 2026-10-29): read them as plain entries with their question. A compass session’s `did_goal` answers “Are you closer to what matters to you?”; a horizon session ends in a `reflection` recording and has no yes or no.
- **Dropped tables:** before 2026-10-29 the database also held highlights, measures, journeys, milestones (the older kind), roadblocks, photos, embeddings, and more (`lib/db/migrations/20261029040745_core_loop_drop_cut_tables.sql:1-8`). They are not needed to rebuild the Logbook. Their text is encrypted under domains not listed in section 3 and is out of scope for version 1 readers.
- **A missing `milestones` table** (archives from 2026-10-29 before that migration): section 10.3.
- **Missing columns:** check with `PRAGMA table_info` and treat an absent column as null (for example `sessions.sprint_id`, added 2026-10-02).
- **No key row, or a key row under an older passphrase:** section 7.1.

## 11. Integrity checklist for a reader

1. Outer zip has a `*.yearwego.header.json` and a `*.yearwego.data.encrypted`; otherwise it is not a YearWeGo backup.
2. `backupFormatVersion` is `1` and `kdfParams` are the expected values.
3. The blob starts with `YWG1` and `01`.
4. AEAD opens the inner zip; failure = wrong passphrase or damaged file.
5. `manifest_hash` matches; each entry exists, has its `size`, and matches its `checksum`. Report failures and keep going: the AEAD tag already vouches for the inner zip as a whole.
6. The database opens as SQLite.
7. The key row opens with the passphrase (or an earlier one); its root key matches the key row’s `checksum` in `crypto_keys`.
8. Each DEK matches its `checksum`; each transcript and audio chunk authenticates.

## 12. Known-answer vectors

`docs/archive-format/vectors.json` holds, for fixed keys, nonces, salts, and ids:

- `archive`: the header JSON, the derived archive key, the AAD, and the sealed `YWG1` blob.
- `key_backup`: a `crypto_key_backups` row’s salt, KDF params JSON, derived key, nonce, and ciphertext, with the root key and its checksum.
- `data_encryption_key`: a wrapped DEK and its checksum.
- `transcript`: a transcript id, nonce, ciphertext, and text.
- `audio`: a three-chunk `YWGA` file (two audio chunks and the FINAL marker), with every chunk’s nonce, AAD, and bytes, and the expected ADTS output.
- `checksums`: an entry checksum and a manifest hash.

All byte strings are lowercase hex. The passphrase is `acorn-anthem-bronze-canopy-harbor-lantern-quilt-velvet`.

Golden archives (a complete backup made by the app’s own backup code with the passphrase `TEST`) come from `tests/node/make-golden-archive.test.ts`, run with `MAKE_GOLDEN=1`. They hold made-up entries only.

## 13. Versioning

- `backupFormatVersion` (header) and `backup_format_version` (manifest) move together (`features/backup/consts/backups.ts:4`).
- The `YWG1` blob version byte and the AAD version `v1` move together (`pack.ts:15-17`; `authenticated-context.ts:13-17`).
- `YWGA` has its own version byte (`chunked-recording.ts:44`).
- A database schema change that a reader would notice (a renamed table or column in section 10, a new way of storing words) is a format change too, even when the archive layers are untouched. It needs a line in section 10.5 at the least.
